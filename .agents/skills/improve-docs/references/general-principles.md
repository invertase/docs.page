# General principles

## Excessive claims

Don't use unverifiable superlatives (*best*, *fastest*, *never*, *always*). Don't *ensure* or *guarantee* security or uptime unless it is actually guaranteed. Prefer "helps with security" over "prevents attacks." Cite a source for performance numbers. Don't disparage third-party products.

## Future features and timelessness

Don't pre-announce unreleased features. In product docs, avoid *now*, *new*, *currently*, *soon*, *latest*, *as of this writing*, *eventually*. Document what exists. *New* is OK in dated release notes if you include a date or version.

## Inclusive language

No unnecessarily gendered language (*person-hours*, not *man-hours*). No ableist slang (*crazy*, *sanity-check*, *dummy variable*). No violent or graphic metaphors. Use the singular *they*. Diverse example names — see [names.md](names.md).

## Jargon

Write around figurative jargon (*post-mortem*, *shift left*) unless the audience searches for it. If you keep a term, define it in parentheses or link once. Don't use a slur or a "don't use" word-list term in prose even if it appears in a legacy CLI; show the command in code font and say what it does.

## Prescriptive documentation

Recommend one path. Avoid *should* (ambiguous). Use *must* or an imperative for required actions, *We recommend* for advice, *can* for optional, *might*/*can* for possible outcomes. Describe actual state, not "the value should be true."

## Third-party content

Don't copy text, images, code, or logos from other docs, Wikipedia, or GitHub. Paraphrase and link.
